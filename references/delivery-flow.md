# 交付流程详解

> 完整流程：数据分析 → 必答确认 → 配置生成 → 本地启动准备 → 验证交付。
> 交付节奏：从拿到表格到完成交付的目标 ≤ 15 分钟。超过 15 分钟时继续推进，并用简短话术说明当前阶段和下一步，不把内部排查细节持续发给客户。
> 交付闭环：生成配置、安装依赖、启动服务、验证首页、验证 `/api/office/snapshot?force=1` 连续完成；不要停在“装依赖中 / 待起服务 / 待验证”。只有等待用户扫码授权、等待必答确认、或命令明确失败时，才暂停并说明原因。
> 执行边界：只查当前项目、本 Skill 安装目录、输出目录和用户明确给出的目录；不要全盘搜索。3000 被占用时自动换可用端口，后续启动和验证都使用真实端口。

---

## 第 1 步：表格数据分析（2 分钟内）

读取客户的表格，**既看结构、也看数据**，得出分析结论（作为第 2 步话术的依据）：

**① 结构分析**：
- 有哪些表：逐张列出表名、记录数和可读主线
- 各列能力：人员、事项名称、状态、日期、数值、比例、关联、附件、只读/可写
- 推荐一个页面主入口表：用于人员工位、默认列表、负责人调整和新增事项写回；未被选中的表仍作为全量数据表参与分析

**② 数据分析**（带着结论去问客户）：
- **全量概况**：表数、记录数、可读主线和需要用户确认的关键列
- **人员旅程**：按人聚合其在全量表中的关联记录、状态分布、可计算进展和关键数值
- **事项/对象情况**：围绕主入口表展示可写回事项，同时把其他表的关联记录进入详情
- **异常点**：负责人字段为空、日期格式异常、可计算指标缺少来源字段、写回字段为只读等
- **写回可见性**：新建/调整页面必须让主入口表字段可见；可写字段可填，不可写字段置灰并说明不能写回原因

**③ 得出分析结论**（第 2 步话术直接用）：
> 例如："共读取 4 张表、120 条记录；建议以「<表名>」作为页面主入口表，因为它同时有事项名称和负责人。其他表会进入全量分析和详情展示。"

**注意**：读表要**快速**（结构 + 关键统计），不逐条翻数据；分析结论要**具体、可验证**；发现的问题（超期/0 任务/字段异常）在对话中一并提及。

## 第 2 步：收集必答信息 + 告知注意事项（一次完整反馈）

> **规则：用户必须回答完所有必答项并明确确认，才允许进入第 3 步。未确认前不生成、不部署。**

**表格权限（要链接时确认，不阻塞生成）**：
- 生成阶段**可读即可**——任何权限形态的表格都能分析并生成页面（读取数据不依赖编辑权限）。
- **写回闸门 = 表格分享权限是否为「互联网上获得链接的人可编辑」**：是 → 双向同步全通；否（未开启 / 仅可阅读）→ 一律只读，写回被拦下（无论账号是谁，含表主本人）。
- 向用户要链接时说明："生成页面只需可读；如需在页面写回（调整负责人/新增任务），请把表格分享权限设为「互联网上获得链接的人可编辑」；未开启或仅可阅读时，页面只能查看与互动。"

**① 先分析表格，得到事实**（不展示给用户，作为话术依据）：
- 有哪些表、每张表的记录数和可读主线
- 每张表的人员、事项名称、状态、日期、数值、比例、关联、只读/可写列
- 推荐的页面主入口表、可选人员档案表、可选项目表
- 人数、状态分布、可计算进展、关键数值、异常点
- 新建/调整时哪些字段可写、哪些字段只读展示及原因

**② 一次回答中向用户反馈以下全部内容**（话术基于①的分析结论，非固定模板）：

> 已收到您的多维表格，我先做了数据梳理：
>
> **数据概况**
> - 全量：共 <T> 张表、<R> 条记录
> - 人员：识别到 <N> 人
> - 建议页面主入口表：「<表名>」（用于工位、默认列表、负责人调整和新增事项写回）
>
> **⚠️ 注意到的情况**（如有）：
> - <如：有 2 条超期任务 / 有 1 人无任务 / 某字段为空>
>
> 开始前需要您确认 5 件事：
>
> **0. 主入口确认**（必答）
> 我会读取全部表并纳入分析展示。为了生成可写回的互动页面，还需要确认一个**页面主入口表**：<表X>。它只决定工位、默认列表、负责人调整和新增事项写回；其他表不会丢弃，会进入全量概览、人员旅程和详情展示。
>
> 可选：人员档案表=<表Y 或 无>；项目表=<表Z 或 无>。没有独立人员表就说"无"（成员会自动从主入口表负责人列聚合）；有人员档案表时，成员池会合并「主入口负责人 + 人员档案表 + 管理员」，地图最多展示 8 人，超出人员仍进入分析和调整候选。
>
> **1. 请写出「事项名称」那一列的字段名**（必答）
> 表格里哪一列代表"这条记录叫什么"（如「任务名称」「销售单号」「客户名称」「工单标题」），请把**那一列的列名**原样写出来。我们**完全按您写的列名使用**，不做任何猜测。
>
> **2. 请写出「负责人」那一列的字段名**（必答）
> 表格里哪一列代表"这条事项由谁负责/谁经办"，请把**那一列的列名**原样写出来（例如「负责人」或「经办人」或「处理人」或「销售员」）。
> 我们**完全按您写的列名使用**，不做任何猜测或映射——页面工位、任务统计、写回全部按这一列。
>
> **3. 谁是表格管理员（表格维护人）？**（必答）
> 该人员将作为 Office Live 小剧场的**管理员**，可进行人员任务分配、调整负责人等操作；其他人只能查看档案。
>
> **4. 人数确认**：当前共 <N> 人，**地图最多展示 8 人（含管理员）**；其余成员仍进入数据分析和负责人调整候选。您确定继续生成吗？（必答）
>
> **补充说明（重要提醒）**：
> - 管理员操作（调整负责人/安排任务/新增任务）需要输入管理口令，口令为「<表格名称>」
> - 互动玩法、查看档案：全员可用，无需口令
> - 📌 **表格权限**：请把表格分享权限设为「互联网上获得链接的人可编辑」——这样页面才能和表格实时双向同步（您在表格里改，页面自动更新）；未开启或仅可阅读时，页面只能查看与互动。您不需要再做任何其他授权操作。

**③ 等待用户逐项确认**：
- 确认页面主入口表、可选人员档案表、可选项目表（**以用户确认为准，不做任何猜测**）→ 确认负责人字段（**以用户写出的列名为准，不做任何映射**）→ 确认管理员姓名 → 确认接受 8 人限制
- 全部确认后，才进入第 3 步

**部署时传参**：把用户确认的表名与列名作为参数传给 `deliver.mjs`：
```
node scripts/deliver.mjs --base <base_token或链接> --admin <管理员姓名> [--code <管理口令>] --task-table <页面主入口表名> [--member-table <人员档案表名>] [--project-table <项目表名>] --owner-field <负责人列名> --name-field <事项名称列名>
```
脚本会**完全按这些确认的表名/列名**确定主入口和写回字段；同时自动把 Base 内其他表作为全量数据表纳入读取、画像、概览、人员旅程和详情展示。没有独立人员表/项目表就不传对应参数。

**对话纪律**：
- 未确认完，不生成配置、不进入本地启动
- 用户对某项有异议（如字段不对、超 8 人）→ 先解决，再继续
- 全程不暴露：代码、密钥、部署细节、平台信息

## 第 3 步：生成配置（1 分钟内）

改写页面模板里的 `lib/office-config.ts`，只改：

```
baseToken    = 客户表格的 Base token
ownerName    = 客户表格管理员姓名（第 2 步确认）
adminCode    = 管理口令（默认取客户表格名称）
tables[].id  = 各表 ID（如字段名不同，同步改 fields 映射）
```

**字段映射规则**（逻辑语义 → 客户真实字段名）：
- 主入口：name 事项名称 / owner 负责人 / status 状态 / due 截止日期 / project 分组或项目
- 人员：name 姓名 / role 角色 / level 职级
- 项目或分组：name 名称 / status 状态
- 若客户字段名不同，按实际字段名填；未映射到语义位的字段也必须以原字段进入全量展示、折叠详情和新建表单
- 读取展示不限制字段类型；写回时才区分可写/只读。可写日期、文本、数字、选项、关联等字段要可填；lookup、公式、自动编号、创建/更新时间等只读字段要置灰展示并说明原因，不能直接隐藏。

**配置生成阶段只改配置**：除 `office-config.ts` 外，不改动其他业务代码文件。

> 详细映射与配置示例：见 [config-guide.md](config-guide.md)

## 第 4 步：本地启动准备（2-4 分钟，全自动）

```bash
# 在页面模板目录（templates/page/）
cd 模板目录
# 一键生成（deliver.mjs 自动完成：授权检查→读表→生成配置→本地模式准备→验证）
node scripts/deliver.mjs --base <base_token或链接> --admin <管理员姓名> [--code <管理口令>] --task-table <页面主入口表名> [--member-table <人员档案表名>] [--project-table <项目表名>] --owner-field <负责人列名> --name-field <事项名称列名>
```

- deliver.mjs 自动完成全部准备，输出本地启动指引（`npm run dev` / `npm run build && npm start`，打开真实端口）
- **首次生成时**：deliver.mjs 会输出**飞书授权链接/二维码**并退出。用户扫码 → 网页点「同意」后，agent 先运行 `lark-cli auth status --json --verify` 验证授权，再重跑同一条 `deliver.mjs` 命令继续生成。不要让命令长时间停在授权等待中。
- **不要向用户要凭证**：全程不需要任何应用凭证/密钥/应用标识，授权通过自动弹出的扫码链接完成
- 详细步骤与排错：见 [deployment.md](deployment.md)

## 第 5 步：验证交付（1 分钟内）

1. 启动页面 → 页面正常加载（HTTP 200）
2. 调 `/api/office/snapshot?force=1` → 返回表格的真实数据（任务数/成员数正确，`source: feishu`）
3. 确认人数：有任务成员数 ≤ 7
4. **验证写回**：实际新增一条测试任务（写回表格成功后再删除），确认表格可写、双向同步可用；中文字段和姓名必须用 UTF-8 JSON body 或临时 JSON 文件提交，避免 shell 编码误判
5. 输出本地访问地址 + 一句话说明："数据来自你的飞书表格，改表格页面自动更新"

**交付结论口径**：不要把“依赖安装中”“服务待启动”“接口待验证”作为最终结果。依赖安装耗时就继续等；开发服务启动后继续测首页和快照；写回失败时区分权限只读、字段只读、字段格式不支持，并给出明确结论。

**端口规则**：本地页面优先使用 3000；如果 3000 已有残留服务，自动改用下一个可用端口。最终回复必须给出真实链接，不要继续验证 `http://localhost:3000` 旧服务。

**限流规则**：遇到飞书细粒度限流时自动退避重试。短暂限流不能直接降级为静态数据，也不能让用户手动等待或重跑。

## 时间预算表

| 步骤 | 预算 | 超时信号 |
|---|---|---|
| 表格数据分析 | 2 min | 表结构复杂/字段难认 |
| 必答信息确认 | 1 min | 用户不回复/问题过多 |
| 生成配置 | 1 min | 字段映射困难 |
| 本地启动准备 | 2-4 min | 网络慢/构建失败 |
| 验证交付 | 1 min | 数据对不上 |
| **合计** | **≤ 15 min** | — |

> **超时处理**：15 分钟内为正常节奏；超过 15 分钟继续推进，并主动汇报当前阶段、下一步和是否需要用户动作。不要把内部排查过程当作连续进度汇报。

## 客户表格适配

### 标准结构（任务 + 人员表齐全）
最快路径：只需换 baseToken + ownerName，字段名基本一致 → **10-15 分钟**。

### 表格更简单（缺表/缺字段）
- 只有一张可作为主入口的表：人员从主入口表负责人列自动聚合（页面仍可用）
- 有独立人员档案表：成员池必须合并主入口负责人、人员档案表和管理员，不能因为成员当前没有事项就从概览或调整候选里消失。
- 缺项目/风险/里程碑表：页面隐藏对应区域，不影响核心功能
- 缺日期/状态字段：页面显示"未填写"，不报错

### 表格更复杂（多表/多字段）
- 主入口字段用于写回，其他表和其他字段作为全量数据进入画像与详情展示，不忽略
- 若关键字段语义无法确认，集中问用户一次；非关键字段保留原字段展示，不硬猜

**原则**：能自动识别就自动识别，识别不了就降级，只对"管理员是谁"这类影响产品逻辑的问题才问客户。
